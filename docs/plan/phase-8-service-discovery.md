# Phase 8 — Ecosystem service discovery

Automatically keep a short, searchable description of every service (git repo) under
the ecosystem root, generated by an LLM from the repo's own docs/structure, refreshed
when it goes stale — so any session, on any service, can ask "what does service X do"
or "which service implements Y" instead of having to `ls` around the ecosystem folder
or ask the human. Built on the same three legs as phase 5.3 (memory) and phase 6
(library): a `runSystemTurn` extraction call, the shared `EmbeddingClient` (Voyage,
graceful no-key degradation), and the in-process Spring AI MCP server phase 5.3
already stood up at `/api/mcp/memory`.

## Why this is a small feature, not a fourth big subsystem

The three requested capabilities map directly onto precedent already in this repo:

| Ask | Precedent it reuses |
|---|---|
| 1. Regenerate a per-service description + embedding when missing/stale, triggered at session close | `ReflectionRequested` event off `SessionService.close()`, `runSystemTurn`, `EmbeddingClient` (5.3) |
| 2. Tool: get description by service folder | Shape of `memory_read` (5.3) / `list_services` (7.4) |
| 3. Tool: find service folder by natural-language functionality query | Hybrid dense+sparse RRF search (5.3's `MemoryRepository.search`) |
| Central on/off switch | `memory.enabled` / `library.sync-enabled` persisted-setting pattern |

The "service folder" registry itself already exists —
`GitWorktreeService.findRepos(root)` (git repos directly under a root, used today by
`MetaController.services()` for the create-dialog picker and by
`OrchestrationMcpTools.listServices` for 7.4's fan-out) — this phase adds a
description + embedding *on top of* that existing enumeration, it doesn't reinvent it.

## Decisions

1. **Storage: a DB-only cache row per service, no Markdown vault.** Unlike semantic
   memory (5.3), a service description isn't curated human knowledge worth an
   Obsidian-compatible file — it's a disposable, cheaply-regenerable summary of what
   the repo's own docs/structure already say. One `service_profile` row per
   `repo_path`, no filesystem component, no sync-from-disk job.
2. **Write posture: auto-write immediately, no approval gate.** Contrast with 5.3
   decision 14 (memory reflection *does* gate on human approval): that gate exists
   because semantic memory is a durable, human-curated store other sessions are asked
   to *trust as fact*. A service description is neither durable (regenerated every
   ~2 weeks or on demand) nor a claim of fact beyond "here's what the repo's own docs
   say" — closer to the skill library's auto-import-and-index posture than to memory's.
3. **Trigger: session close (per spec) + a manual rediscover action**, not a scheduled
   background sweep. Close-triggered discovery only ever touches services someone
   actually opens a session on, so a service nobody works on would otherwise never get
   a description — the manual action (§ Frontend) backfills that gap on demand, the
   same role the library's manual "Scan" plays relative to its own scheduled sync.
   A scheduled ecosystem-wide sweep was considered and rejected for v1: it would
   silently burn an LLM call per untouched service on a timer with no one watching,
   for a capability the manual action already covers on demand.
4. **Skip regeneration when the repo hasn't actually changed, even if stale — gated by
   the git commit, not a content hash of the digest.** (2026-09-06 revision: the
   original draft computed a `digest_hash` by reading the digest inputs and hashing
   them, then skipped the LLM call if unchanged — but that still means reading files
   on every close-triggered check just to find out nothing changed.) Instead, before
   rendering anything, run `git rev-parse HEAD` (single O(1) subprocess call
   regardless of repo size — the existing `GitWorktreeService`/`GitOpsService`
   pattern) and compare against the stored `last_commit_sha`; unchanged → bump
   `discovered_at` and return, with **no digest read and no LLM call at all**. Only a
   changed SHA (or no row yet) proceeds to render the digest and spend a system turn.
   Cheaper and more correct than folder mtimes, which get bumped by a checkout/clone
   with no content change. Trade-off: this only sees *committed* state — uncommitted
   working-tree edits don't trigger a refresh — which is the right call for a
   periodically-regenerated cache describing a service's committed state, not its WIP
   scratch. A repo with zero commits (no `HEAD`) falls back to always regenerating.
5. **Staleness threshold, model, and the central switch are persisted settings**
   (`service-discovery.enabled` default **true**, `service-discovery.staleness-days`
   default **14** per spec, `service-discovery.model` default `haiku`) — same
   Settings-dialog-editable, no-restart-needed pattern as every other knob in this app.
6. **The shared in-process MCP server's attachment condition generalizes.** Today
   `SessionService` attaches the `memory` mcpConfig entry (→ `/api/mcp/memory`) only
   when `memory.enabled`. That endpoint is really a shared tool server — 7.4's
   orchestration tools already live there too, unconditionally alongside memory's.
   This phase adds a second, independently-toggled tool set to the *same* server, so
   the attachment condition becomes `memory.enabled || serviceDiscoveryEnabled()`
   (whichever is on attaches the one shared entry — never two entries for the same
   URL, which would just double-expose every tool under two prefixes). Each tool
   still self-gates on its **own** setting inside the method body (`memory_search`
   already gates dense search on `embeddings.configured()`; the same idiom now covers
   "feature administratively disabled but the shared server happens to be attached
   for the other feature"), so `service-discovery.enabled=false` genuinely disables
   the two new tools even when `memory.enabled=true` keeps the server attached.
   No new endpoint, no sidecar change, no PROTOCOL.md entry — this is backend
   (Postgres + REST + MCP tools) and frontend only.
7. **Tools are scoped to the calling session's own visible ecosystem**, exactly like
   `list_services` — both new tools take a required `sessionId` (5.3 decision 12b's
   precedent: no transport-context plumbing, just a validated argument) and the
   backend resolves `session.ecosystemPath()` to filter which `service_profile` rows
   a call may see/search, via the same `worktrees.findRepos(...)` call `list_services`
   already makes. A session with no `ecosystemPath` (no wider context configured, or a
   Codex session — 5.13 always nulls `ecosystemPath` for that provider, the same
   existing limitation `list_services` already has) sees nothing; nothing new to fix.
   Claude sessions get both tools pre-approved in `allowedTools` (read-only, same
   rationale as memory's decision 10); Codex goes through the normal approval flow.
8. **Digest inputs, not agentic exploration.** Rather than let the system session use
   tools to explore an arbitrary repo (slower, harder to bound/test), the backend reads
   a small bounded digest itself — README/CLAUDE.md/AGENTS.md (first ~4 KB each),
   a manifest name+description sniff (`package.json`/`pom.xml`), and a depth-≤2
   directory listing (skipping `.git`/`node_modules`/`target`/`dist`/`build`) — and
   packs it into one prompt, same pattern as the library's `LibraryAiService` AI-fill.
   The prompt asks for a description that names major subsystems and *where* they
   live (paths), since that's what makes ask 3 ("where is X implemented") resolvable
   at service granularity from one embedded blob per service.

## Storage model

### Schema — `V12__service_discovery.sql`

```sql
CREATE TABLE service_profile (
    id            UUID PRIMARY KEY,
    repo_path     TEXT NOT NULL UNIQUE,   -- canonical absolute path (matches session.repo_path)
    name          TEXT NOT NULL,          -- basename, refreshed each run, display only
    description   TEXT NOT NULL,
    tags          TEXT[] NOT NULL DEFAULT '{}',
    last_commit_sha TEXT,                 -- git rev-parse HEAD at generation time; unchanged => skip everything
    embedding     vector(1024),           -- null when Voyage unconfigured
    tsv           tsvector GENERATED ALWAYS AS (
                    setweight(to_tsvector('english', name || ' ' || description), 'A')) STORED,
    discovered_at TIMESTAMPTZ NOT NULL,
    session_id    UUID,                   -- triggering session; null for a manual scan; no FK (sessions may be pruned)
    created_at    TIMESTAMPTZ NOT NULL,
    updated_at    TIMESTAMPTZ NOT NULL
);
CREATE INDEX ON service_profile USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON service_profile USING gin (tsv);
CREATE INDEX ON service_profile USING gin (description gin_trgm_ops);  -- pg_trgm already enabled by V9
```

## Discovery flow (`ServiceDiscoveryService`)

1. **Trigger**: `SessionService.close()` — right where it already does
   `if (session.reflectionEnabled()) events.publishEvent(new ReflectionRequested(id))`
   — gains a sibling, gated on the setting rather than a per-session flag (this
   feature has no per-session opt-out, per the "central setting" ask):
   ```java
   if (settings.serviceDiscoveryEnabled()) {
       events.publishEvent(new ServiceDiscoveryRequested(id, session.repoPath()));
   }
   ```
   consumed by an `@EventListener` on a virtual thread (close() never blocks on it).
   Manual: `POST /api/service-discovery/services/rediscover {repoPath}` calls the same
   `discover()` with `force=true`, synchronous (bounded by the system-turn timeout,
   ~45 s like AI-fill), 404 if `repoPath` isn't a real repo.
2. **`discover(repoPath, sessionId, force)`**:
   - No-op if `!settings.serviceDiscoveryEnabled()`, if `repoPath` doesn't exist or
     has no `.git`, or if another discovery for the same `repoPath` is already in
     flight (a small `ConcurrentHashMap<String,Boolean>` guard — two sessions on the
     same service closing near-simultaneously shouldn't race two system turns).
   - Skip if `!force` and an existing row's `discovered_at` is within
     `service-discovery.staleness-days`.
   - Run `git rev-parse HEAD` in `repoPath` (decision 4). If a row exists with the
     same `last_commit_sha`, just bump `discovered_at` and return — no digest read,
     no LLM call. `force` still respects this (rediscovering an unchanged repo is
     cheap and correct to skip the LLM call for, it just refreshes the timestamp).
     A repo with no commits yet (command fails) falls through to regenerate.
   - Only now render the digest (`ServiceDigest.render(repoPath)`) and spend one
     system turn (model per `service-discovery.model`, same `set_model`-round-trip
     override `runSystemTurn` already supports for 5.3's reflection model): digest
     in, strict JSON `{description, tags[]}` out — same `stripFences`/validate
     pattern as ticket import / library AI-fill.
   - Embed `name + description` best-effort (`EmbeddingClient`, skipped without a
     Voyage key). Upsert the `service_profile` row (`ON CONFLICT (repo_path)`),
     `discovered_at = now()`, `last_commit_sha` = the SHA just resolved,
     `session_id` = the triggering session (null for manual scans that aren't tied
     to a close).
3. **Failure posture**: best-effort, like reflection — a failed turn or invalid JSON
   logs and leaves any existing row untouched; never surfaces back to `close()`.

No session-journal event, no WS message, no sidecar involvement — this is invisible
inside the closing session's own transcript by design (§ Frontend covers where a human
actually sees it).

## MCP tools (`ServiceDiscoveryMcpTools`, same shared server as memory/orchestration)

| Tool | Args | Returns |
|---|---|---|
| `list_discovered_services` | `sessionId` | `[{servicePath, name, description, tags}]` for every service in this session's visible ecosystem that has a profile — an overview when the agent doesn't have a specific functionality to search for yet; not-yet-discovered services are omitted (2026-09-06 addition) |
| `service_description` | `sessionId`, `servicePath` | `{name, description, tags, discoveredAt}`, or a clear "not yet discovered" error if `servicePath` has no row yet or isn't in the session's visible ecosystem |
| `find_service` | `sessionId`, `query` | ranked `[{servicePath, name, description, score}]` — hybrid dense (cosine, skipped without Voyage) + sparse (FTS + trigram) RRF fusion, restricted to `service_profile` rows whose `repo_path` is in `worktrees.findRepos(session.ecosystemPath())` |

All three throw immediately (before doing any work) if `!settings.serviceDiscoveryEnabled()`
— decision 6's self-gating. Injection: the existing `withDefaultMemoryMcp()` (renamed
in spirit, not necessarily in code, to "shared in-process tools") now attaches whenever
`memory.enabled || serviceDiscoveryEnabled()`; `allowedTools` gets
`mcp__memory__list_discovered_services` / `mcp__memory__service_description` /
`mcp__memory__find_service` appended independently of the existing three memory-tool
names, Claude only.

## Settings

New `SettingsService` keys (Settings dialog → new "Service discovery" section):
`service-discovery.enabled` (default true), `service-discovery.staleness-days`
(default 14, floor 1), `service-discovery.model` (default `haiku`).
`SettingsController`'s request/response records grow the matching three fields —
same mechanical addition as every prior settings batch.

## Frontend

- **Settings dialog**: new section, three controls as above.
- **New topbar dialog** (small, one view — no import/sources tab complexity like
  Library): service list — name, path, description, tag chips, discovered-at + a
  "stale"/"never discovered" badge, per-row **Rediscover** button (`POST
  .../rediscover`, `force=true`) and **Edit** button. A **"Scan ecosystem now"**
  button iterates the already-fetched list client-side and calls rediscover
  sequentially only for rows that are missing or stale — same chunked-with-progress
  UX as the library's bulk AI-fill, and it's why no separate bulk backend endpoint is
  needed: the frontend loop *is* the bulk operation.
- **Manual edit** (2026-09-06 addition): Edit swaps the row into a description
  textarea + tags input; Save calls `PATCH /api/service-discovery/services
  {repoPath, description, tags}` (`ServiceDiscoveryService.updateDescription`), which
  writes the given text directly — no system turn — and re-embeds it. It also stamps
  the repo's *current* commit SHA (same `git rev-parse HEAD` call `discover()` makes),
  so the hand-edit slots into the existing skip-logic exactly like a real discovery
  result: it stands as an override until the next commit, at which point
  auto-discovery is free to regenerate over it — the same "editing is a veto, until
  content actually changes" posture memory's hand-edited vault files have, achieved
  here for free by reusing the commit-SHA gate rather than a second mechanism.
- `GET /api/service-discovery/services` backs the list: for every repo returned by
  the existing `/api/repo/services` enumeration, left-joined against `service_profile`
  by `repo_path`, so never-discovered services show up with a null description rather
  than being invisible.
- `rest.ts` methods, `protocol.ts` types (`ServiceProfileView`), `SettingsDialog` section.

## Out of scope for this pass

- Per-session opt-out (memory has `reflectionEnabled`; this feature is
  central-setting-only per the ask).
- Scheduled background sweep (decision 3) — the manual action covers the gap.
- File-level (sub-service) indexing — tool 3 asks for "which service," not "which
  file"; the digest's "where subsystems live" guidance (decision 8) gives enough
  resolution for that without a second retrieval granularity.
- Session-journal visibility (`session_event` rows) for a discovery run — it happens
  after/around close, often with no client attached; the new dashboard dialog is the
  intended surface, not the transcript.
- Cross-ecosystem-root visibility beyond a session's own `ecosystemPath` (matches
  `list_services`'s existing scoping, decision 7).

## Tasks

1. **Schema** — `V12__service_discovery.sql` as above; entity/repository record.
2. **Digest renderer** — `ServiceDigest.render(repoPath)`: README/CLAUDE.md/AGENTS.md
   sniff + truncate, manifest name/description sniff, depth-≤2 directory listing
   (reuse the containment/skip-dirs conventions from the library scanner). No hash —
   change detection is the git commit SHA (decision 4), computed separately and
   cheaply before this ever runs.
3. **`ServiceDiscoveryService`** — `discover(repoPath, sessionId, force)` per the flow
   above (including the `git rev-parse HEAD` gate, `GitWorktreeService`-adjacent
   subprocess pattern); `ServiceDiscoveryRequested` event + `@EventListener`;
   in-flight guard.
4. **`ServiceProfileRepository`** — `JdbcClient` style (`MemoryRepository`/
   `TemplateRepository` are the models): upsert-by-repo_path, `findByRepoPath`,
   `listAll()` (for the dashboard join), `hybridSearch(query, embedding, visiblePaths, limit)`
   (RRF, same shape as `MemoryRepository.search` restricted to `kind=all` semantics
   but no scope/tag dimension — just the visible-paths filter).
5. **Settings** — three new `SettingsService` keys/getters/setters;
   `SettingsController` request/response fields.
6. **MCP tools** — `ServiceDiscoveryMcpTools` (`list_discovered_services`,
   `service_description`, `find_service`); generalize the shared-server attachment
   condition in `SessionService` (`memory.enabled || serviceDiscoveryEnabled()`);
   independent `allowedTools` append for Claude sessions.
7. **REST** — `ServiceDiscoveryController`: `GET /api/service-discovery/services`
   (join against `/api/repo/services`'s enumeration), `POST
   /api/service-discovery/services/rediscover {repoPath}`, `PATCH
   /api/service-discovery/services {repoPath, description, tags}` for the manual
   hand-edit (`ServiceDiscoveryService.updateDescription` — writes directly, re-embeds,
   stamps the current commit SHA so the edit participates in the skip-logic).
8. **`SessionService.close()`** — the `ServiceDiscoveryRequested` publish, gated on
   `settings.serviceDiscoveryEnabled()`, alongside the existing reflection publish.
9. **Frontend** — Settings section; new topbar dialog (list + Rediscover + Edit +
   "Scan ecosystem now"); `rest.ts`/`protocol.ts` additions.
10. **Docs** — `CLAUDE.md` (settings table, new dialog icon), `docs/ARCHITECTURE.md`,
    `docs/plan/README.md` phases table + decision log entry (this doc supersedes
    nothing; net-new).

## Definition of Done

- Close a session on a service with no existing `service_profile` row →
  within moments a row appears with a sane description (mentions real subsystems from
  that repo's actual README/structure) and (with a Voyage key set) a non-null
  embedding.
- Close a second session on the *same*, unchanged service before the staleness window
  elapses → no new system turn is spent (verify via app log / no new LLM call),
  `discovered_at` unchanged.
- Manually set `discovered_at` far in the past (or wait out a short test staleness
  value), edit and **commit** a change to the repo's README → next close (or manual
  Rediscover) produces an updated description and a new `last_commit_sha`. Editing the
  README **without** committing does not trigger a refresh (decision 4's known
  trade-off).
- From a **different** session on a **different** service in the same ecosystem, call
  `find_service` with a natural-language description of functionality that actually
  lives in the first service → it's ranked first; `service_description` on its
  `servicePath` returns the same description text; `list_discovered_services` returns
  every discovered service visible to that session (short description each), omitting
  any that haven't been discovered yet.
- A session with no `ecosystemPath` configured gets empty results from all three tools;
  a **Codex** session gets the same three tools, going through normal approval (not
  pre-approved).
- Dashboard **Edit** on a service: change the description/tags and Save → writes
  immediately (no system turn spent, verify via app log), `find_service` on a phrase
  from the new text now ranks it, and the underlying `last_commit_sha` matches the
  repo's actual current commit. Closing another session on that same, still-unchanged
  service afterward does **not** overwrite the hand-edit (commit SHA still matches).
- Turning `service-discovery.enabled` off: close-triggered discovery stops firing, and
  the three tools become unreachable/error even in a session where `memory.enabled` is
  still on (proves decision 6's self-gating, not just non-attachment).
- Dashboard dialog lists every ecosystem service including never-discovered ones;
  per-row Rediscover and "Scan ecosystem now" both work; Settings changes take effect
  without restart.
- Without `CLAUDE_UI_VOYAGE_API_KEY`: descriptions still generate, `find_service`
  degrades to sparse-only (still returns sane results for a query containing an exact
  identifier from the description), `service_description` unaffected.

## Manual test script

1. Ensure an ecosystem root with ≥2 real git repos is configured (Settings →
   Sessions). Settings → Service discovery: confirm defaults (enabled, 14 days,
   haiku); temporarily set staleness to a small value (e.g. 0) for faster iteration.
2. Create a session on service A (`ecosystemPath` = the ecosystem root), do a small
   amount of work, close it. Open the new dashboard dialog → service A shows a
   populated description within moments; `psql`: `service_profile` has one row,
   `last_commit_sha` set, embedding non-null if Voyage is configured.
3. Create and close a second session on service A immediately → no new LLM call
   (check `logs/claude-ui.log` for the discovery skip vs. a system-turn log line);
   `discovered_at` bumped only if staleness was already 0 forcing a re-check, but
   `last_commit_sha` identical → description text unchanged, and note no digest was
   even read (the skip happens before that step).
4. Edit **and commit** a change to service A's README (add a distinctive fake
   sentence), close a third session on it (or hit Rediscover) → new description
   reflects the edit; `last_commit_sha` changed.
5. Create a session on service B (same ecosystem root), ask it to find where the
   distinctive functionality from step 4 lives via natural language → transcript shows
   a `find_service` call ranking service A first, then a `service_description` call
   confirming the text; ask it to list every known service → `list_discovered_services`
   call, response includes service A (and any other already-discovered services) with
   short descriptions, omitting undiscovered ones.
5a. In the dashboard dialog, click **Edit** on service A, change the description to
    include a second distinctive fake phrase, Save → app log shows no new system turn;
    ask the service-B session to `find_service` on that new phrase → ranks service A.
    Close another session on service A without touching its files → the hand-edit
    survives (commit SHA unchanged, so discovery just bumps `discovered_at`).
6. Restart with no `ecosystemPath` on a fresh session (empty ecosystem field) → all
   three tools return empty/error, confirmed in transcript.
7. Repeat step 5 on a **Codex** session on service B → same three tools available, but
   each call requires manual approval (not pre-approved), same as any other Codex tool.
8. Turn `service-discovery.enabled` off in Settings; close a session on a third,
   never-touched service → no row is created. With `memory.enabled` still on, open a
   session and try `find_service`/`service_description` directly → tool call errors
   ("service discovery is disabled"), proving the self-gate rather than mere
   non-attachment.
9. In the dashboard dialog, click "Scan ecosystem now" with several services stale →
   progress shown, only stale/missing ones get rediscovered sequentially; a fresh
   service is skipped. Click a single row's Rediscover on an already-fresh, unchanged
   service → `discovered_at` bumps, no LLM call (`last_commit_sha` unchanged).
10. Unset `CLAUDE_UI_VOYAGE_API_KEY`, restart, repeat step 5 with a query containing an
    exact identifier from the description (not a paraphrase) → `find_service` still
    ranks it via the sparse arm.
